1. Overview

ASPClassic Portal is a Blazor Server modernization of CrudePortal, an ASP Classic / VBScript application built on the AdminLTE template. The original is 4,144 lines of VBScript across 11 pages and 9 server-side includes; the port is 19,765 lines of C# and Razor.

The application is a metadata-driven CRUD portal. It has no screens of its own in the usual sense: a screen is a row in a database table. The DataView table names a table to edit, its primary key and what operations are permitted; the DataViewField table names the columns, their labels and how each should be rendered. One generic page reads that metadata and produces the grid, the form, the filters and the buttons. Adding a screen means adding rows, not writing code.

The portal edits itself. Four built-in views, with negative IDs, point at the portal's own metadata tables: -1 Manage Data Views edits DataView, -2 Data View Fields edits DataViewField, -3 Data View Actions edits DataViewAction and -4 Navigation edits Navigation. Understanding this is the single most useful thing when reading either codebase — the same generic page renders both the application's data and its own configuration.

What the port preserves

The metadata model is carried over unchanged, including the exact meaning of every flag bit, the negative IDs of the built-in views, and the placeholder syntax used by action buttons. The portal.* tables, their columns and their seeded rows are reproduced faithfully, so a view defined against the legacy database describes the same screen here.

What the port changes

The legacy rendered HTML on the server and relied on jQuery DataTables in the browser for paging, sorting, filtering and export, posting form data back to ajax_dataview.asp. In Blazor Server there is no round trip to cross: the grid is a server-side component, the dialog calls a service directly, and values never become text and are never parsed back. The ajax_dataview.asp endpoint therefore has no equivalent — its responsibilities are distributed across the services described in section 5.

EF Core is used for the metadata, not for the data. The 16 typed entities cover the portal's own configuration tables. The tables a data view edits are unknown at compile time — MainTable is a string in a database row — so those are read and written through raw parameterised DbCommands built from the view definition. The Inventory table used in section 8 has no entity and appears in no DbSet, yet the portal renders, filters, edits and exports it.

Why Blazor Server?

The legacy is a server-rendered application whose interactivity comes from jQuery plugins operating on HTML the server produced. Blazor Server keeps that shape: rendering stays on the server, state stays in C#, and the browser holds a connection rather than an application. The alternative — an API plus a SPA — would have meant inventing a JSON contract for metadata that is only ever consumed by the page that renders it, and reintroducing the parse-and- serialise round trip that ajax_dataview.asp existed to service.

The cost is that every interaction is a network message, and that a component instance survives a change of query string. Both have consequences that are called out where they arise.

3. How to Build and Run

Prerequisites

  • .NET 10 SDK
  • Visual Studio 2022 (17.12+) or any editor with the .NET CLI
  • No database server — SQLite is file-based and the schema is created on first run

Build and Run Steps

cd ASPClassic
dotnet build ASPClassic.sln
dotnet run --project ASPClassic

Or press F5 in Visual Studio. The launch profile serves:

SchemeURL
HTTPShttps://localhost:7248
HTTPhttp://localhost:5248

Port selection is not arbitrary. Windows reserves blocks of ephemeral ports for Hyper-V and WinNAT, and those reservations are reshuffled on reboot. A port inside a reserved range fails to bind with SocketException 10013 — the host exits before it listens and Visual Studio reports only "unable to connect to web server". Check with netsh interface ipv4 show excludedportrange protocol=tcp before choosing a port.

Startup Sequence

Program.cs performs three steps against the database before the pipeline starts:

#StepDetail
1EnsureCreatedAsync()Creates the schema from the EF model if the file is absent. No migrations.
2seed-data.sqlThe rows harvested from the legacy database project — the portal's own configuration.
3demo-data.sqlDemonstration content added for this port. Runs after the seed, so it can also remove seeded rows.

Both scripts are executed through a raw DbCommand rather than ExecuteSqlRawAsync. That overload treats its SQL as a composite format string, and seeded values legitimately contain braces — stored templates such as {{urlparam[dataview[search]]}}. Passed to String.Format they raise FormatException before a single row is written, and the host terminates at startup.

Deleting aspclassic-dev.db is a safe reset: schema, seed and demo data are all rebuilt on the next start.

Log Files

Serilog writes to logs/aspclassic-{Date}.log beside the executable, and to the console. The database check is exposed at /health.

Query-string changes do not re-initialise a component. Navigating from ?ViewID=-2 to ?ViewID=1 is the same page: Blazor reuses the instance and calls OnParametersSetAsync, never OnInitializedAsync again. Every page whose content depends on the query string therefore loads in OnParametersSetAsync, guarded on a signature of its parameters so a render pass does not re-query. Loading from initialisation alone leaves the address bar showing one record and the page showing another, with nothing to indicate a fault.

Page Catalog

Dataview — the generic screen

The heart of the application. Given ?ViewID=n it loads the view definition, decodes its flag bitmasks, loads the field and action lists, and renders a MudBlazor data grid with a toolbar. Add, edit, clone and delete open AjaxDataviewDialog. Accepts per-column filters as <FieldIdentifier>[search]=value, which is how a shared screen is narrowed to one parent.

Browse

The single-record view. Reads the same metadata; redirects to dataview when the view's Enable Browse Module flag (256) is not set, exactly as the legacy did.

Typed CRUD screens over DataView and DataViewField, using EF entities rather than the generic engine. AdminDataviewfields also hosts Auto-Initialize, which reads a table's columns and generates the field rows for any not already described.

5. Services (Business Logic)

All services are registered Scoped in Program.cs. In Blazor Server a Singleton is shared across every user’s circuit, so scoped registration is a correctness requirement rather than a preference. Data access uses IDbContextFactory<ASPClassicVBScriptDbContext> and creates a context per operation — a component’s lifetime is not a unit of work.

The write path

SaveDataviewRecordAsync composes a parameterised INSERT or UPDATE against the view’s MainTable. Values are always parameters; table and column names come from the view definition and are checked against the view’s own field list, so nothing supplied by a request can reach the statement as SQL. The view’s Allow Add and Allow Edit flags are enforced here, and a statement affecting zero rows is reported as a failure rather than a success.

On insert, a blank optional field is omitted from the statement rather than written as NULL. The legacy opened the row with AddNew and set only what was posted, letting the column’s DDL default apply; writing NULL explicitly defeats that default and fails outright on a NOT NULL column that has one.

The Metadata Model

Three columns carry most of the meaning, and conflating them is the most common mistake when working on this application:

ColumnIsIs not
DataView.MainTableThe table the screen editsCreated by the portal — it must already exist
DataViewField.FieldSourceThe database columnThe name used in URLs or form inputs
DataViewField.FieldIdentifierThe client-side name — the form input and the grid column name, and what a [search] URL parameter refers toA database column

A field describes a column; it does not create one. There is no ALTER TABLE anywhere in the legacy application. Adding a field for a column that does not exist is accepted by both the legacy and this port, and fails later on the first insert that names it. Add the column to the table first, then describe it — by hand or with Auto-Initialize.

There is no sixth or seventh field flag, and no “allow search” or “RTE” view flag. A decode that invents bits 32 and 64 for fields is reading a different vocabulary from the one the database declares, and will silently mis-render every screen.

7. Security Configuration

The legacy application has no authentication and no authorization: every page is open, and there are no access checks on a data view or an action. The port does not invent a security model it cannot verify against the original, but it does close the gaps that a dynamic-SQL application creates.

ConcernTreatment
SQL injectionEvery value is a parameter. Table and column names come from the view definition, never from a request, and are checked against the view’s declared field list before use.
Permission flagsAllow Add, Allow Edit and Allow Delete are enforced in the service, not only in the toolbar. A hidden button is not a permission check.
Rate limitingFixed window, 200 requests per minute, partitioned by user or host. Returns HTTP 429.
AntiforgeryAddAntiforgery() registered.
Security headersSecurityHeadersMiddleware. New in the port.
Access controlDataViewSecurityHelper is a hook for per-view rules. It currently permits everything, matching legacy behaviour.
AuditAuditLogger records structured entries. New in the port.
HTML encodingSanitizerClass ports the legacy encoders for form, display and querystring contexts.

Before this is exposed to anyone, authentication and per-view authorization have to be added. A metadata-driven portal is, by construction, a general-purpose editor for whatever tables its metadata names — including its own configuration. The DataViewSecurityHelper hook exists for exactly this and is deliberately left permissive so that no false impression of protection is created.

8. Data Notes and Seed Data

Two scripts populate the database at startup, in order, and they have different owners and different rules.

seed-data.sql — harvested, regenerated

The rows the legacy database deploys with: 169 rows across 13 tables, taken from the CrudePortalDB post-deployment script and from the lookup views. These are not sample data — they are the application’s own configuration. Without them a metadata-driven portal starts, serves every route and renders nothing at all, with no error to explain it, because an empty table is not a fault.

The file is regenerated by the migration tooling on every run, so it must not be hand-edited. Its statements are guarded — each row is written only if its key is absent — and nothing is deleted, so re-running is harmless and rows added since are never touched.

The lookup tables are the interesting case. In the legacy they are views over literal VALUES lists: there is no table underneath and nothing ever inserts into them, so the rows are the definition. Materialised here as ordinary tables, their rows have to come from somewhere, and that source is the view definition itself. Their column types are inferred from the literals — an unquoted 1 is a number and 'Text' is not — because typing them all as text would leave every lookup’s identifier a string while the column that stores it is an integer, and the two could never be joined.

demo-data.sql — hand-written, permanent

Demonstration content added for this port, kept separate precisely because the harvested seed is overwritten. It runs after the seed, so it can also remove seeded rows.

ContentPurpose

Adding a screen: the whole flow

StepWhereWhat
1DatabaseCreate the table. The portal never issues DDL.
2Manage Data ViewsAdd a row naming MainTable and Primarykey, and set the permission flags. It appears in the sidebar once published.
3Manage FieldsDescribe the columns — by hand, or with Auto-Initialize, which reads the table and generates a row per column not already described.
4Manage FieldsAdjust labels, set Show in Items List for grid columns, and point lookup fields at their linked table.

Auto-Initialize infers the field type from the column type and marks NOT NULL columns required. It does not set Show in Items List, so a generated field appears in the form but not the grid until that is ticked.

A SQLite fidelity note. The legacy maps %char to Text and %text to Text Area. SQLite reports both as TEXT, so Auto-Initialize produces Text Area for every textual column. The field type is easily changed afterwards, but the divergence is a property of the target database, not of the port.

10. Key Modernization Patterns

Dynamic SQL from metadata → parameterised DbCommand

The legacy built SQL by string concatenation from view metadata. The port keeps the dynamic shape — it must, since the table is a value in a row — but separates the two kinds of input. Identifiers come from the view definition and are validated against its declared field list; values are always parameters. The distinction is what makes a metadata-driven query safe.

ADO updatable recordset → composed INSERT / UPDATE

rsItems.AddNew, field assignment, rsItems.Update becomes a composed statement. The subtlety is that a recordset only sets what you assign, so unassigned columns take their DDL default — behaviour reproduced by omitting blank optional fields from the insert rather than writing NULL.

DataTables client-side grid → server-side component

Paging, sorting, filtering and search move from jQuery DataTables into DataViewQueryEngine, executed as SQL. The URL contract is preserved: <FieldIdentifier>[search]=value still filters a named column, which is how the Fields and Actions buttons scope a shared screen to one parent view.

Placeholder expressions → resolved server-side

Action URLs stored in the database use {{row[Column]}} and {{urlparam[name]}}, resolved in the browser by the legacy’s JavaScript. They are now resolved on the server against the clicked row and the current address, and legacy *.asp targets are translated to routes.

DataTables export buttons → HTTP endpoint

Export moves to /aspclassic-vbscript/export/{viewId}, because a Blazor circuit is a websocket and cannot hand the browser a file. The current filters travel with the request, so the file matches what the screen is showing. Excel receives SpreadsheetML with numeric cells typed as numbers; CSV carries a UTF-8 BOM so Excel reads the encoding rather than guessing.

Response.Redirect → NavigationManager

Blazor performs a redirect by throwing NavigationException, which the framework catches. A page that wraps its load in catch (Exception) — the natural shape when porting error handling around a Response.Redirect — intercepts that first: the redirect never happens and the page reports a failure for something that worked. Every such handler is filtered with when (ex is not NavigationException).

Server-side includes → components and services

An include that rendered markup becomes a component; one that held logic becomes a scoped service. Where an include did both, it becomes both.

On reading this codebase. Almost every defect found during this port was of one shape: two sides of a contract generated independently, each internally plausible, with nothing checking that they agree. A dialog that collected values and a writer that never existed; a page that discarded rows and an engine nothing called; a column name used where a form-input name was meant. When something renders but shows nothing, the fault is rarely in the thing you are looking at — it is in the join between it and the thing that feeds it.
